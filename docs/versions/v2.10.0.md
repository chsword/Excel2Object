# v2.10.0

发布日期：2026-09-15

## 概述

本版本新增流式导出：逐行取数据并写出，内存中只保留若干行，导出所占内存不再随行数增长。为此，自动列宽与按值合并的计算方式一并改为在写入过程中完成，数据因而只被遍历一遍。

## 变更明细

### 1. 新增：流式导出

此前的导出一律先在内存中建好整个工作簿，再整体转成 `byte[]`。行数达到十万量级时，工作簿与字节数组同时驻留内存，占用相当可观。

新增的 `ObjectToExcelStream` 逐行取数据并写出，写过的行随即离开内存：

```csharp
using var file = File.Create("orders.xlsx");
new ExcelExporter().ObjectToExcelStream(ReadOrders(), file, options =>
{
    options.ExcelType = ExcelType.Xlsx;
    options.FreezeHeader = true;
    options.MergeRepeatedColumns.Add("省份");
});
```

`ExcelHelper` 上有同名的静态方法，`DataTable` 亦有对应重载：

```csharp
ExcelHelper.ObjectToExcelStream(orders, stream, options => options.AutoFilter = true);
ExcelHelper.ObjectToExcelStream(dataTable, stream);
```

在 ASP.NET Core 中可直接写入响应体，不必先在内存中备好整个文件的字节数组：

```csharp
[HttpGet("orders.xlsx")]
public IActionResult Download()
{
    // Kestrel 默认不允许同步写入响应体，而 NPOI 的写入是同步的，故按请求开启
    HttpContext.Features.Get<IHttpBodyControlFeature>()!.AllowSynchronousIO = true;

    Response.ContentType = "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet";
    Response.Headers.ContentDisposition = "attachment; filename=orders.xlsx";
    ExcelHelper.ObjectToExcelStream(ReadOrders(), Response.Body, o => o.ExcelType = ExcelType.Xlsx);
    return new EmptyResult();
}
```

数据源逐行取用，因此可以是数据库游标、迭代器等不宜全数载入内存的序列。传入的流由调用方负责关闭，本方法不会关闭它。

需要说明的是，**省下的是内存，不是等待时间**：写过的行落到临时文件，而最终的 `.xlsx` 包（其本身是个 zip）要等数据取完才一次写入调用方的流。上面那个接口不会一边生成一边向浏览器送出内容，它的意义在于生成十万行的文件时不必把整个工作簿连同字节数组一并留在内存里。

本机实测（五列，含文本、金额与日期，net8.0）：

| 行数 | 内存导出 | 流式导出 |
| --- | --- | --- |
| 5 万 | 245 MB / 2.6 秒 | 89 MB / 2.2 秒 |
| 20 万 | 710 MB / 6.4 秒 | 89 MB / 3.7 秒 |

流式导出的内存占用不随行数增长：被刷出内存的行写入临时文件，导出结束时删除。

### 2. 前置条件：应用需自行引用 SkiaSharp

流式写入基于 NPOI 的 SXSSF，后者每把一行刷出内存，都要先测量一次默认字符宽度，而这一步用的是 SkiaSharp。NPOI 把 SkiaSharp 列为**不随包传递**的依赖，应用若未自行引用，运行时将无从加载。

```xml
<PackageReference Include="SkiaSharp" Version="3.119.2" />
<!-- Linux 上另需本机库；Windows 与 macOS 的由 SkiaSharp 自带 -->
<PackageReference Include="SkiaSharp.NativeAssets.Linux.NoDependencies" Version="3.119.2" />
```

本库不替使用方引入该依赖：它会为每个运行时标识带来数十兆的本机库，而只用内存导出的使用方本无须为此付出代价。缺失时，`ObjectToExcelStream` 会在任何内容写出之前抛出 `Excel2ObjectException`，说明需要引用哪些包，而不是在写下若干行之后抛出一个与 Excel 无关的 `FileNotFoundException`。

### 3. 流式导出与内存导出的差别

各项特性在流式导出下同样生效：冻结表头、自动筛选、下拉、条件格式、样式表、公式列、按值合并与指定区域合并，均有用例覆盖。两处差别需要说明：

- **仅 `.xlsx` 能够流式写入。** `.xls` 的格式决定了必须先在内存中建好再写出，此时 `ObjectToExcelStream` 只是把结果写进流，并不省内存。该格式至多 65,536 行，本也不适合大文件。
- **文本不进共享字符串表，而是直接写在单元格里。** 这是 SXSSF 的做法：共享字符串表要把所有不重复的字符串留在内存中，与流式写入的初衷相悖。读的一侧不受影响，Excel 与本库的导入都照常；文件体积则取决于数据——重复值多时会略大，各不相同时反而略小。

内存中保留的行数由 `StreamingRowWindow` 指定，默认 100：

```csharp
options.StreamingRowWindow = 500;
```

该值并非越小越好：行一旦刷出内存即写入临时文件，此后不可再读回，它同时决定了写入过程中可回看的范围。取值须为正数，否则抛出 `Excel2ObjectException`。

### 4. 改进：自动列宽与按值合并改在写入过程中算出

这两项此前都要回看数据：自动列宽先把数据遍历一遍量出宽度，再从头写入；按值合并在全部写完之后逐格读回工作表，找出连续相同的值。流式导出下两者都行不通——先前的行已不在内存中。

现改为写入时逐格记下：宽度随写随量，合并的各段随写随记，写完即可落定。除了使流式导出得以成立，内存导出亦因此少走一遍数据。

### 5. 改进：多张长下拉列表一次写入隐藏工作表

超过 255 字符的下拉列表放不进数据验证本身，须写到隐藏工作表上，一张列表占一列。此前逐张写入，第二张要回头从首行开始再写一遍；在流式写入的工作表上，这些行已被刷出内存，那一列会悄然丢失。现改为收齐全部列表后逐行填满各列，一次写完。

### 6. 流式导出下的跨表公式

公式列可以引用同一工作簿中已有的表（见 v2.1.0），本库为此要读出那张表的表头，以便把列标题换算成列号。流式导出时 SXSSF 只是套在工作簿外面的一层，随 `SourceExcelBytes` 带进来的表，其行并不在这一层里，读到的表头因而为空，公式会被判为「引用了不存在的列」。现改为向底下的工作簿去取表头：

```csharp
using var output = new MemoryStream();
new ExcelExporter().ObjectToExcelStream(thisMonth, output, options =>
{
    options.ExcelType = ExcelType.Xlsx;
    options.SheetTitle = "本月";
    options.SourceExcelBytes = lastMonthBytes;
    options.FormulaColumns.Add(new FormulaColumn
    {
        Title = "环比",
        Formula = c => c["金额"] - c.Sheet("上月")["金额"]
    });
});
```

## 行为变更

- **数据源只被遍历一次。** 此前开启 `AutoColumnWidth` 时，`ObjectToExcelBytes` 会把数据遍历两遍（一遍量宽度、一遍写入），只能遍历一次的序列因而不可用。现在两个入口都只遍历一遍。
- **数据源抛出的异常改在写入过程中浮现。** 行的取值由「建模型时全部取完」改为「写一行取一行」，`GetValue` 等处抛出的异常因而发生在导出过程中，而非导出开始之前。所有情形下调用方收到的仍是同一个异常。
